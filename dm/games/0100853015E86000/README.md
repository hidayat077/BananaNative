# No Man's Sky (`0100853015E86000`)

Base game v5308416 (display 7.10.0), SDK 20.5.17, Hello Games' own engine with Havok and Wwise, on NVN. Modules `main` and `sdk`; `rtld` is replaced by the host. The package is a `.nup` read in place: its RomFS is 99 `NMSARC*.pak` archives (3.71 GB), with no BNSH / BAHS at the top level.

Status: reaches in-game (~12–24 fps on Turnip on Snapdragon 870 / Adreno 650, `TU_DEBUG=nolrz`) with 0 missing shaders; paused after initial graphics fixes (GPU BCn alias propagation active, remaining visual polish and performance tuning open). A full split finds 10,349 distinct shaders (3,548 vertex, 6 geometry, 6,666 pixel, 129 compute); the Vulkan library translated all of them and every module passed `spirv-val --target-env vulkan1.3`. The rewriter patched `main` (2.0 MB, 74 gates) and `sdk` (0.7 MB, 109 gates) for Android. `sdk` is build `0023a1b0…`, the same build [STEINS;GATE RE:BOOT](../01008BC024FDE000/README.md) ships, so that profile is the closest reference for the SDK layer.

## Survey

- Code: `main` 32.5 MB of text, 41.7 / 6.9 / 1.5 MB segments, 26.4 MB bss, build ID `157fa464786a74d276a8ec7da9d5a385`; `sdk` build `0023a1b06130cd795f7bc4613772af0a`. `main.npdm` reports program ID `0100853015E86000` and 0 MB of system resource.
- SDK strings: `NintendoSDK_nnSdk-20_5_17`, `NintendoSDK_NVN-20_5_17`, libcurl and libz of the same version. `sdk` imports 863 of the host's 1,248 HLE hook names; `main` imports 510 symbols new to the compared game, among them `nv::InitializeGraphics`, `nv::SetGraphicsAllocator`, `nvnBootstrapLoader` and the `nn::ro` loader.
- Rewrite-site census (`insn_census.py`): `main` 10,928,830 instructions, 44,530 x18 uses, 809 `mrs tpidr_el0`; `sdk` 1,674,226 instructions, 58 `svc` (one of each number 1–0x1d, 0x1f, 0x21–0x2f except 0x2b, 0x2e, 0x30, 0x31, 0x37–0x3f, …), 15,571 x18 uses, 124 `mrs tpidrro_el0`, 43 `mrs cntpct_el0`.
- All 99 RomFS files are `.pak`; the largest are `NMSARC.audio.pak` (1.65 GB), `NMSARC.MeshPlanetBIOMES.pak` (436 MB), `NMSARC.MeshCommon.pak` (425 MB), `NMSARC.TexUI.pak` (102 MB) and `NMSARC.Shaders.pak` (22 MB). The survey reads no BNSH / BAHS header at the root.
- The survey was made without extracting the RomFS: the `.nup`'s code modules were copied (39 MB) and a manifest of path, size and the first 32 bytes of each RomFS file was fed to the repository's own survey code. The report lives in the game's work folder, beside the `.nup`, outside the repository.

## Shaders

- The 99 `.pak` files are Hello Games' HGPAK archives: a header (`HGPAK\0\0\0`, version 2, file count, chunk count, compressed flag, data offset), a 32-byte-per-file index (MD5 of the path, offset, decompressed size), an array of compressed chunk sizes, then the data in 0x20000-byte Oodle chunks on Switch. The first member is a CRLF-separated manifest of the other 21,166 paths.
- `NMSARC.Shaders.pak` holds 21,117 `.nvb` files (and 49 GLSL source `.bin` files). Each `.nvb` is one NVN program: its control section starts with magic `0x98761234`, holds its own length at `+0x20` and the code area's length at `+0x704`; the code area starts at magic `0x12345678` (graphics) or `0x12345679` (compute), with the SPH word at `+0x30`. The stage comes from the SPH word, so no name parsing is needed.
- [Whole-file Oodle chunks in Hello Games' HGPAK archives](../../../docs/reference/shaders.md#whole-file-oodle-chunks-in-hello-games-hgpak-archives): `shader_split.py` now reads HGPAK members and `.nvb` records through `oodle()` (`DM_OODLE_OOZ` on a PC), and skips paks whose manifest has no `.nvb`, so the 1.65 GB audio pak is not inflated. A chunk whose stored size is already 0x20000 is kept whole, not sent to the decoder.
- The full split writes `shader_map.tsv`, `shader_facts.tsv`, `shader_pairs.tsv` and `pso_pairs.tsv` into the profile. The map's sources name the `.nvb` members inside `NMSARC.Shaders.pak`, so a targeted split can read them straight from the `.nup` too.
- The Android Vulkan library has 18,475 modules (10,349 base, 5,589 `uint`, 2,525 `uint_mixed`, 12 `shuffle_lds`) in 136.1 MB (559.7 MB of SPIR-V before compression); chain `a3d8757f9bcd`, Vulkan chain `0f9e17c20bc3`, inputs `ab8fa1812c3e`. The pack is 222.7 MiB; the RomFS stays in the game's `.nup`.

## Found on this game

- **FSR2 lock compute shader's RGB10A2 storage image read as unbound / wrong channel unpacking (`7b0a750b4d5993b7`, updated fix pending phone retest):** originally every run logged eight `[RED] vk: shader 7b0a750b4d5993b7 binding 2: texture ID … has no view of shape 0x81 (storage)` lines for 1088x612 NVN `0x3d` (RGB10A2 UNORM) images (`serial 35031/35032`). Adding `A2B10G10R10_UINT_PACK32` to `class_twin` removed the red line in `0100853015E86000-20261126-033350.log`, and `bug.nvncap` confirms the pre-FSR2 `852x480` color buffer (`serial 35142`) is clean while the `1088x612` lock/post-process buffers show the artifact: `7b0a750b4d5993b7`'s SPIR-V declares `OpTypeImage ... R32ui` and bit-extracts `R10`/`G10`/`B10` from `.x`, which `A2B10G10R10_UINT_PACK32` unpacked across `.rgba` and zeroed in bits 10..31. `id_view` (`vka_tex.c`) now binds `VK_FORMAT_R32_UINT` / `R32_SINT` for integer storage bindings of 4-byte packed colour formats ([Packed 10:10:10:2 images bound as integer storage images on the Vulkan replay](../../../docs/reference/rendering.md#packed-1010102-images-bound-as-integer-storage-images-on-the-vulkan-replay)).

- **BC textures bound straight to image slots read as unbound (`genmipmap_comp_compressbc*`, resolved on Turnip):** every run logs eight `[RED] vk: shader … has no view of shape 0x1 (storage)` lines for serial 8, a 16x16 BC1 sparse texture (`flags 0x20`, `usage 0x7`), from `6f6576c98dcc83ed` (`genmipmap_comp_compressbc1`), `7f19e3052ceb6c32` (BC7), `7367d4768248db2b` (BC4) and `215e08021cc6eb0f` (BC5). The compute shaders' block writes went nowhere, so mip levels stayed stale — the likely cause of the murky/low-detail close-up terrain. `vka_tex.c` now uses an uncompressed block alias for these bindings and copies the blocks back after the dispatch; after `55f6207` one `has no view of shape 0x81` line remained from the same texture's integer sampled-image binding, which is now covered too ([A BC texture bound directly to an image slot reads as unbound on the Vulkan replay](../../../docs/reference/rendering.md#a-bc-texture-bound-directly-to-an-image-slot-reads-as-unbound-on-the-vulkan-replay)). Found in logs `0100853015E86000-20261126-031421.log` and `0100853015E86000-20261126-034328.log` (Adreno 650, Turnip v27); `d486cf0` removed every red line and copy-back covers levels 0–2. The phone's system driver advertises Vulkan 1.1 and the host requires Vulkan 1.3, so forcing it black-screens; no system-driver run is expected for this game.

- **FSR2 composite ghosting / corruption (`fsr2switch_comp_fsr2cs_lock_0`):** a frame captured at 75 s (`bug.nvncap`, frame 1856, 3.0 GB) shows block-shaped ghosting/corruption in the `1088x612` FSR2 history/combine targets (`serial 35033/35034`) while the pre-FSR2 `852x480` color buffer (`serial 35142`) and `640x360` depth reprojection (`serial 34679`) are clean. Root-caused to the `A2B10G10R10_UINT_PACK32` vs `R32_UINT` storage-image mismatch in `7b0a750b4d5993b7` (`fsr2switch_comp_fsr2cs_lock_0`) above; pending phone retest. Changing the Upscaler setting (`DM_VK_NDSR`, tried by the player) and enabling `render_cond` in the profile (`9ea003c5`, reverted in `df179e68` because it changed nothing) had no effect. All logs are on Turnip.
- **GPU-compressed BC1/3/4/5/7 textures corrupted on Exosuit (neon green / RGB static), partially verified on phone (`425b3e1d`):** `genmipmap_comp_compressbc1/3/4/5/7` compute shaders write 4x4 compressed blocks into `format 0x2f` (`R32G32B32A32_UINT`) and `format 0x17` (`R32G32_UINT`) storage images (`ceil(w/4) x ceil(h/4)`) over the same pool memory (`mem`) as `w x h` BCn textures. `vka_tex.c` (`vka_tex_id_bc_sync`, `vka_tex_get`) and `vka_draw.c` (`vka_dispatch`) now propagate GPU-written blocks to aliased BC images in both creation orders ([Compute shaders writing BCn blocks into uncompressed storage images over the same memory](../../../docs/reference/rendering.md#compute-shaders-writing-bcn-blocks-into-uncompressed-storage-images-over-the-same-memory-android)). On the phone run on Turnip (`2026-11-25`, 5,127+ frames, 12–22 fps), both `BC alias init` (16 logged, 1–5 levels) and `BC alias sync` (16 logged at `lv 0`) fired with 0 skipped levels and 0 crashes; close-up first-person planetary terrain still looked murky/low-detail and third-person Exosuit / system driver were not yet retested.
- **62+ missing pixel shaders (`program stage 1 is not in the shader library`), resolved:** dumping the runtime shaders via `DM_NVN_SHDUMP` showed all 62 matched existing `ps_shaders.bin` entries except byte `+0x718` of the control section (`early_fragment_tests`), toggled from `0` to `1` at run time. `vka_shader.c` now falls back to `prog_key_alt` (`+0x718 = 0`) ([Runtime `early_fragment_tests` flag (+0x718) changes pixel shader keys](../../../docs/reference/shaders.md#runtime-early_fragment_tests-flag-0x718-changes-pixel-shader-keys)). Confirmed on phone: 0 missing shaders, terrain and world render cleanly.
- **Startup hang polling `nvnSyncWait(sync, 0)` before first present (`main+0x240b0d4` / `0x240b1a8`), resolved:** on frame 0, before calling `nvnQueueFenceSync` or `nvnWindowAcquireTexture`, the renderer polls `nvnSyncWait` on newly initialized `NVNsync` objects until the result is not `TIMEOUT_EXPIRED`. `nvnSyncWait` now returns `NVN_SYNC_WAIT_RESULT_ALREADY_SIGNALED` for unfenced syncs ([`nvnSyncWait` on a newly initialized sync returns already signaled](../../../docs/reference/nvn-objects.md#nvnsyncwait-on-a-newly-initialized-sync-returns-already-signaled)). Confirmed on phone: reaches in-game (~24 fps).
- **SIGSEGV at `addr=0x200` (`main+0x2483248`) and `nvnDeviceRegisterFastClearColorui` stub, resolved:** `nvnTextureBuilderGetStorageClass` and `nvnTextureGetStorageClass` returned `0`, causing the engine to treat sparse virtual-pool allocations as non-sparse, call `nvnMemoryPoolMap` on the `0xf40000000`-byte `VIRTUAL | CPU_NO_ACCESS` pool (`NULL`), and pass `NULL + 0x200` to `memcpy` when uploading a 16x16x1 3-level texture ([Texture storage classes are non-zero](../../../docs/reference/nvn-objects.md#texture-storage-classes-are-non-zero)); `nvnDeviceRegisterFastClearColori` and `nvnDeviceRegisterFastClearColorui` are now implemented in `hle_nvn.c`. Confirmed fixed on phone (reaches first frame submission).
- **SIGSEGV writing into `argv[0]`, resolved:** with the heap fixed, the second phone run reached `nnMain` and faulted at `main+0x1300e0` (`lr=main+0x1300dc`), writing into `libnxhost+0x92e70`, a read-only host string holding `"game"`. The game lowercases its argument strings in place; the host had handed it a literal instead of writable memory ([An argument string the host keeps read-only](../../../docs/reference/services.md#an-argument-string-the-host-keeps-read-only)). `argv[0]` is now a writable `static char[]` in `dm/host/main.c`. Needs a rebuilt APK and a confirming run.
- **Startup abort, resolved:** the first phone run aborted in `nninitStartup` at `main+0x2614c58` with `nn::diag` Result `0x1003`. The log's `[mem] SetHeapSize 0xc9400000 + modules 0x5c00000 > app pool 0xcd500000 (used memory reported 0x4000000 + bss 0)` is the known [heap-sized-from-used-memory case](../../../docs/reference/memory.md#heap-sized-from-the-application-pool-less-used-memory): the game takes its heap as pool − used memory, but the host checks the request against the real 92 MB of rewritten modules. The profile now reports `mem_used 0x6000000` (96 MB), as [Catherine: Full Body](../0100BF00112C0000/README.md) does for the same module size. Needs a rebuilt APK and a confirming run.
