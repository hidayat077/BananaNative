# Hogwarts Legacy (`0100F7E00C70E000`)

Snapshot v327680, SDK 17.5.4 (`SDK_libz-17_5_4-Release0`), Unreal Engine 4 (the `Phoenix` cook, `UE4CommandLine.txt` points at `Phoenix.uproject`), NVN. Modules `main`, `subsdk0` (`NintendoSDK_movie`), `sdk`; `rtld` is replaced by the host. The source is a 14 GB `.nup` read in place — the RomFS was not extracted into the repository or the home folder.

Status: the lit scene was fixed on the phone (2026-11-23, realme RMX3371 with Turnip, library `0f9e17c20bc3`): boots, 30 fps, UI and world draw correctly. The NaN first blamed for it was a red herring. The real cause was Unreal's material textures: type-1 texture handles in the game's uniform buffers with their samplers in c2 were left without a slot by the translator, so materials read 0 and the picture tonemapped to black. [The fix](#the-black-scene-is-missing-material-texture-slots-2026-11-23) is ported from the Peanuts Native fork (`c2fc9bf`), which plays this game with the same pack. The remaining sound fault — voices and music 15-20 dB low — is [the sdk's Opus decoder reading this game's own libopus tables](../../../docs/reference/audio.md#the-sdks-opus-decoder-read-the-games-libopus-tables), also ported from that fork (`9b7811b`); a phone check of the new host is pending.

## Shaders

`shader_split.py` reads the `.nup` in place (`<file>.nup:base/romfs` and `:base/exefs/main`) with `DM_UE_DECODE` and the `ooz` worker (`DM_OODLE_OOZ`, built from `dm/third_party/ooz`). The IoStore shader libraries decode locally on Linux — no Mac needed. The split finds **65,047 shaders** (5,597 compute, 9 geometry, 38,350 pixel, 21,091 vertex; 61,979 game and 3,068 global), with 21,091 variation pairs; the tables are in this profile. The Vulkan build made 83,431 SPIR-V modules (all `spirv-val`-valid); 2 of the 65,047 shaders could not be translated because they declare more bindings in one stage than the driver reports, so those draws will be missing until the binding limit is raised. The library is 737 MB (3.1 GB of SPIR-V before compression).

## Android pack

`pack_android.py` reads the `.nup` directly (`<file>.nup:base/romfs`); the work folder is beside the package (`<folder>/0100F7E00C70E000-work/android-pack`). The rewrite of `main` is the slow step (about 37 minutes), then the 703 MB library is copied in. The pack is 880 MiB and holds the rewritten `main` / `subsdk0` / `sdk`, the build-ID gates, and the shader library. The RomFS stays in the `.nup`.

## Phone run: dark lit scene (fix pending phone check, 2026-11-23)

On Turnip the game reaches its frame loop, runs at about 30 fps with audio and draws ~441 draws a frame. The UI renders correctly, but the lit world is almost black; brightening a screenshot shows the geometry is all there (character, walls, railings), only unlit. With the system driver the screen stays black and nothing renders (not investigated further at the reporter's request). There is no `[RED]` line beyond the ADPF hint failure, no missing-shader request (both `shaders/layer/req/` and `files/shader_req/req/` stayed empty apart from an unrelated older South Park dump), no texture-cache eviction and no skipped draws after the pipeline warm-up.

A frame capture at 40 s (frame 716, `dark.nvncap`, 770 MB) is a **loading screen** (a still castle image with a HINT line), not an in-game 3D frame. A capture at 90 s (frame 2146, `ingame.nvncap`, 880 MB) is the broken in-game frame: HUD and film grain draw, the 3D world is black. Its `TPIX` chunks were decoded directly (chunk header `cap_tpix` 168 bytes + one `cap_tsub` 48 bytes, then level-0 pixels). Of the four 1280x720 `NVN_FORMAT_R11G11B10F` targets, the early one (serial 5908) has **0 NaN** texels, while the two in-game scene targets (serials 26400 and 26423) have **433,858 NaN texels each (47% of the frame)** and serial 26422 has 63,149 NaN and 758,292 all-zero texels. A decoded view of serial 26400 still shows the character and walls, so geometry is drawn; the colour values are what is broken. This is the strongest lead for the dark picture: a tonemap fed NaN yields black while the unlit HUD is unaffected.

`DM_VK_NANSCAN` found a real fault: **about 60–120 NaN texels per frame in the 1280x720 `R11G11B10F` scene colour target** (serial near 5948), always starting near (1132, 344) and carried into the following passes. Whether those texels are what darkens the in-game picture is still unproven. `DM_VK_NANSCAN=2` with a one-draw step narrowed the first appearance to a draw that uses vertex shader `b9c0e2fde8bbda7c`; skipping pixel shader `8e4ad8a13590b1bd` did not remove the NaN, and the vertex shader is common to every NaN line. That vertex shader's module fetches float4 data from two textures (`vp_t_cb196610_1056805A` / `_1056805C`) and feeds it to `OpFma`; whether the NaN comes from the fetched data or from the translation is not established. A NaN reaching the scene colour can explain the dark frame if it contaminates the eye-adaptation downsample, as it does in other games ([NaN texels in mip chains](../../../docs/reference/rendering.md#mip-chain-pass-sampling-the-level-it-renders)), but that link is not proven here.

## Found on this game

- [InverseSqrt of zero on the Vulkan replay](../../../docs/reference/shaders.md#inversesqrt-of-zero-on-the-vulkan-replay): a general host patch clamps the operand, and the offline translator now bakes the same clamp into the library (Android chain `e4625cf8f816`). The library was rebuilt with `scripts/shader_fast_rebuild.py` (migrate hack): 39,597 of 65,047 entries re-translated (those with a scalar `InverseSqrt`), 25,448 migrated from the old library; the 706 MB library is in the pack. **Checked on the phone 2026-11-23:** the original NaN writer no longer produces NaN, but the black lit scene has another cause (above).

`DM_VK_NANSCAN=2` with a one-draw step at frame 1000 (in-game) named the first writer: **draw 281-282 of pass 0, vertex `f61fc44ee5ab4906` / pixel `36310803131ac0b6`** (both from `ShaderArchive-Phoenix_Chunk10`, UE5543 / UE5539). The next draw of the same pair raises the target from 10,088 to 182,180 NaN texels. The pixel module was extracted from the built Vulkan library and disassembled: it samples several textures, sanitises NaN UVs with `OpIsNan`, and contains a normalisation `Fma` → `InverseSqrt` (plus two `OpFDiv` by a support-buffer word). An `InverseSqrt` of zero/negative, or a division by zero, would produce Inf/NaN on Vulkan where Maxwell's RSQ may give a finite result. An input-texture scan (`DM_VK_NANSCAN_FS`) spent its whole line budget on frame lines and did not report, so whether a sampled texture or the arithmetic is the source is still open. The capture shows the geometry is drawn; only the values are broken.

Ruled out by A/B on the phone, all with the same result: `DM_VK_CS_ASYNC=0` + `DM_VK_PSO_ASYNC=0`; `DM_UE_TEXTURE_POOL=1000` (not applied: the rewriter does not find `r.Streaming.PoolSize` in this main, `ue_cvar.py` confirms it is not registered with the known pattern); `DM_VK_EAGER_TEX=1`; `DM_VK_SUBGROUP_PIN=0`; `DM_VK_PUSH_DEDUP=0` + `DM_VK_DRV_MEMO=0`; `DM_VK_TEX_TRACK=0`; a new save. The two shaders the build could not translate (`6d69c07dd8606f7e`, `d30cc1c32b57b33f`, both pixel) are not requested during play.

## The dark scene is not the NaN (2026-11-23, phone A/B)

The `InverseSqrt` clamp removes the NaN but **does not fix the black picture**. With an `DM_VK_SPV_OVERRIDE` that clamps all seven `1.0/x` results of pixel shader `56aa7ed34e604447` to ±1000 and scrubs non-finite outputs, `DM_VK_NANSCAN=1` logged **0 NaN/Inf results over 2100+ frames** — and the lit scene was still black. The NaN was real but a red herring for this symptom.

Ruled out since, each with the picture still black (key=screenshot or log evidence):
- **The tone map.** `DM_VK_SPV_OVERRIDE` multiplying the three colour stores of the final fullscreen pass (`5fd19bc6a635d625`, vertex `7a76e9bed4736078`) by 64 showed only amplified dither noise and darker NPC silhouettes: the values reaching the tone map are already ~0. The tone map's constant buffers from `DM_VK_UB_PEEK` were plausible (inverse resolution, colour matrix, transform).
- **The lit shader's own inputs.** `DM_VK_UB_PEEK=36310803131ac0b6` showed plausible constant buffers. `DM_VK_TEX_STATS` on that shader (live, `DRAWS=8`) showed all nine sampled textures finite, with two exceptions below.
- **Depth rejection.** A new Android diagnostic `DM_VK_DEPTHOVR` (commit `5b54496e`, the Vulkan counterpart of `nvn_mtl.m`'s `DM_NVN_DEPTHOVR`) forced `op 7` = ALWAYS on the light-volume draws. The targets stayed black. Code review of `vka_draw.c` confirms the NVN→Vulkan depth mapping (`dfv - 1`) and blend mapping (`bfac`/`bop`) are correct and unchanged since import: `op 6` is `GREATER_OR_EQUAL` from NVN `GEQUAL`, and `blend 1(6,7,0/0,7,0)` is ordinary `SRC_ALPHA / ONE_MINUS_SRC_ALPHA / ADD`, not dual-source.
- **The pipeline cache.** `DM_VK_PCACHE=0` made no difference.
- **One light shader.** Forcing `147f9bb7a3c2d4c8` to write `(1,1,1,1)` did not change the light targets; that pass has at least six other pixel shaders (`1a904f71…`, `7f5a0b29…`, `7728cca8…`, `fda96e9e…`, `d96541a6…`), all sharing vertex `24532fead836a5ef`.

**Live finding that narrowed it:** forcing pixel shader `36310803131ac0b6` to red turned the *background* red while the NPCs and cave walls stayed black silhouettes. So geometry and the replay pipeline work; several different lit shaders cover the scene, and the remaining ones still receive no light. `DM_VK_TEX_STATS` found the concrete anomaly: two 640×360 BGRA8 textures bound to that shader at bindings 271/272 (UE4 slots `10590060` / `1059005C`, serials change per run) are **0 in R/G/B, alpha 1, every frame**. An `rt log` pass clears them to `(0,0,0,1)` and then draws six or more 36-vertex light volumes into both (cull front, depth GEQUAL, write off). This was a symptom, not the cause.

## The black scene is missing material-texture slots (2026-11-23)

The same game plays correctly in the Peanuts Native fork of this project (its note has the full route and measurements). Its investigation found the cause behind every symptom above: Unreal's material textures are **type-1 handles** whose texture word sits in the game's own uniform buffer (c4–c10, arrays of 32 indexed by the draw's primitive) while the separate sampler word sits in driver table c2. `vk_android_build.py classify` had no slot for the texture half (139,302 bindings across nearly every material shader), so the replay bound a null descriptor and every such texture read 0 — normal maps of 0 produced the NaN in `36310803131ac0b6`/`f61fc44ee5ab4906`, and the tone-mapped picture went black. The empty half-resolution light targets were downstream of the same broken materials. [Handles in a game uniform buffer with their sampler in c2](../../../docs/reference/shaders.md#handles-in-a-game-uniform-buffer-with-their-sampler-in-c2-android).

Fixes ported from that fork into this tree (all general, none game-specific):

- `vk_android_build.py ubo_tex_c2_sampler` + `vk_android_spv.py nonuniform_arrays`: the texture half gets its uniform slot, and descriptor arrays read at a computed index get `NonUniform` (the latter is also the fix for the dark 8×8 blocks on Adreno: [A descriptor array read at a per-pixel index without NonUniform](../../../docs/reference/shaders.md#a-descriptor-array-read-at-a-per-pixel-index-without-nonuniform-android)). Both are Vulkan-chain changes; the libraries are being rebuilt for `0f9e17c20bc3`, with `test_vk_android_ubo_tex.py` and `test_vk_android_nonuniform.py` passing.
- `vka_spv_table_pool` + `vka_shader.c`/`vka_bind.c`/`vka_draw.c` tabpool: tables longer than the translator's 32-element array (this game's reflection captures have 512 entries) are read through the texture pool, and the first 32 entries are made before a draw that reads them ([A table of handles longer than the translator's 32-element array](../../../docs/reference/shaders.md#a-table-of-handles-longer-than-the-translators-32-element-array-android)). `DM_VK_TABLE_POOL` (restart) and `DM_VK_TABLE_PREMAKE` (live) turn the two halves off. `t_android_spvpatch`/`t_android_shlib` pass with the new test cases.
- `DM_VK_NANSCAN_NZ=<W>x<H>|<serial>` (this tree's own diagnostic): the per-pass scan already computed non-zero counts for every kind-0 attachment; it now logs them for a filtered target, so a pass that fills or clears a target can be told from one that never writes it.

The fork also fixes this game's texel-buffer view table overflow, one copy per submission of its light grid (13–14 fps after the first spell) and a copy bound after its submission retired (one-frame black plants); those need its newer `vka_tbuf.c` module, which this tree does not have yet. The fork's hardware-Opus fix is ported: the older C interface now decodes with this game's own libopus when a game module exports the plain `opus_*` symbols, with one state per decoder and Nintendo's 8-byte packet header stripped ([the sdk's Opus decoder read the game's libopus tables](../../../docs/reference/audio.md#the-sdks-opus-decoder-read-the-games-libopus-tables)). The log before it showed the symptom: 1,036 frames decoded in 10 s with a peak of only 4,299 of 32,767. `DM_OPUS_SDK=1` keeps the old path. `t_opus_hw` covers both module cases and a failed initialization.

## Open

- Rebuild the shader library for chain `0f9e17c20bc3` (running on the PC), copy it into the phone's pack and rebuild/reinstall the APK; then check the cave scene on Turnip with `DM_VK_NANSCAN=1` (expect no NaN now) and a screenshot. Measure the memory layout (the keys are still survey defaults).
- Port the fork's `vka_tbuf.c` texel-buffer fixes if the symptoms appear here.
- A/B the new 150-draw part default (`DM_VK_CHUNK` / `DM_VK_CHUNK_PASS`, was 600) on this phone: the run is GPU-bound at 19-22 fps with 900-1,200 draws a frame, and the fork measured 47.2 -> 52.5 fps in Breath of the Wild on Turnip at the same size. Both switches are live, so `DM_VK_CHUNK=600 DM_VK_CHUNK_PASS=600` in `env.txt` is the A/B. Keep `DM_VK_RD_GW=1` (default) with the in-pass splits so a uniform word read at bind time sees updates whose copy has already gone to the GPU.
- The two shaders that exceed the stage's binding limit (`6d69c07dd8606f7e`, `d30cc1c32b57b33f`, "more than 64 bindings in one stage") are absent from the library. The profile's `vk_delta.tsv` marks them `-` for this chain, as Mario Kart World's does, so a phone-side **Prepare shaders** succeeds instead of stopping at "did not build: no library written (DMSH_VK_REQUIRE_ALL)" — they are simply skipped if drawn. The general fix is to raise `DMSH_VK_STAGE_BINDINGS` in `dmsh_abi_vk.h` from 64 to 128 (the Metal reflection's `NVN_REFL_MAXB` was raised the same way). A probe that raised it to 128 built both shaders: the largest set-0 binding count in this library is **77** in a pixel shader, so 64 was only 13 short and 128 is enough. That changes both `DMSH_VK_CHAIN` (to `623fcc6dea4a`) and `DMSH_VK_ABI` (to `3a14a3c9c191`), so **every** game's library and the APK must be rebuilt and the device's per-set descriptor limits rechecked on the phone; the bindless pool's reserve also grows (`RESERVE = 5 * DMSH_VK_STAGE_BINDINGS`). Not done here: it would restart this game's 65k-shader rebuild, and those two shaders are not requested in the scenes checked so far.

History of the dead end: the half-resolution light targets, depth override, white light shaders and the raw-attribute vertex passthrough were all tried before the material-texture cause was known; none changed the picture. An offline replayer was built (`replay-agent-build/` in the work folder, with the NDK's toolchain file, pushed under `run-as dev.nxnative.android files/replay/` with `DM_VK_HOOKDIR` at the APK's `base.apk!/lib/arm64-v8a`), but it skips ~410 of ~424 draws, so its GPU dumps cannot identify a writer.
